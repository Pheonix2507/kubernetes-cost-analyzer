MIGRATIONS ARE NOT RUN BY THIS CHART, and that is deliberate.

  There is no init container and no Helm hook that applies them. A migration is a schema change with a
  lock, and running it automatically from every pod start means N replicas racing on the same DDL --
  golang-migrate takes an advisory lock so they serialise rather than corrupt, but the losers then block
  on startup and the rollout stalls without saying why.

  More importantly, a migration is a decision. It should be a reviewed, deliberate step you can time,
  not a side effect of a deploy that happened to restart a pod.

    kubectl run kca-migrate --rm -it --restart=Never \
      --namespace {{ .Release.Namespace }} \
      --image=migrate/migrate --command -- \
      migrate -path /migrations -database "$DATABASE_URL" up

CHECK IT WORKED:

  kubectl -n {{ .Release.Namespace }} rollout status deploy/{{ include "kca.name" . }}-api
  kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "kca.name" . }}-api {{ .Values.api.service.port }}:{{ .Values.api.service.port }}
  curl localhost:{{ .Values.api.service.port }}/readyz

  Or run the whole verification: make helm-verify
